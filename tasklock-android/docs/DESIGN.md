## 1. 仕様内の矛盾・未確定事項と判断

| # | 仕様上の論点 | 判断 |
|---|---|---|
| 1 | §5・§9 は「自由入力」を初期テンプレートに含むが、§7 は MVP を4つに限定 | データ（`TaskTemplates.ALL`）には5つ定義し、MVP の UI には4つだけ表示（`shownInMvp=false`） |
| 2 | §9「UsageStatsManager によるアプリブロック」と §8「AccessibilityService でブロック」 | **ブロックは AccessibilityService、UsageStatsManager は学習時間の検証に使用**。UsageStats によるブロックは下記 §4.3 の理由で Phase 1 では実装しない |
| 3 | 運動テンプレートの Health Connect 連携を Phase 1 に含めるか | **含めない**。Phase 1 の運動は回数の自己申告。Health Connect は権限説明画面・プライバシーポリシー・Play の健康データ申告が追加で必要で、コアフロー検証の優先順位（§8）に反するため Phase 2 |
| 4 | §9 は収益化の実装方針を求めるが、§8 はコアフロー前に課金を作り込まないと規定 | **Phase 1 は方針設計のみ**（§8 本書）。Billing ライブラリは未導入 |
| 5 | 「端末内完結」と Android 自動バックアップ | **バックアップ・端末間転送ともに無効化**。再インストールで履歴は消える（課金は Play から復元できるので影響なし） |
| 6 | ロック中に設定を緩めれば即回避できる | **方式B**: ロック中は解除条件に影響するタスクの追加・削除を禁止（有効タスク0件のときの追加のみ可）。ロック対象から外すのも不可。判定は DB の現在状態から行う（§4「変更の不変条件」） |
| 7 | VERIFIED 必須タスクが計測不能になると永久にロックされる（D2） | **案b**: 有効タスクが1件以上あるなら、自己申告で解除できるタスクを必ず1件以上保持する。VERIFIED 必須タスクを自己申告へ自動フォールバックすることはしない |
| 8 | 学習アプリにロック対象を選ぶと計測できず永久ロック（D1） | 学習アプリの集合とロック対象の集合は交わらないことを Repository（ChangePolicy）で保証。UI でも候補から除外 |

## 2. 技術スタック

| 領域 | 採用 | 理由 |
|---|---|---|
| 言語 | Kotlin | 仕様どおり |
| UI | Jetpack Compose + Material 3 | 画面数が少なく、ナビゲーションライブラリも不要（sealed interface で画面切替） |
| 永続化 | Room（SQLite） | 端末内完結、型付きクエリ、Flow による画面自動更新 |
| DI | なし（`AppContainer` で手組み） | MVP の規模では不要。外部SDKを増やさない方針 |
| ブロック | AccessibilityService | 前面アプリ切替をイベントで即時に受け取れる |
| 検証 | UsageStatsManager（queryEvents） | 学習アプリの前面表示時間の計測 |
| 外部SDK | **なし**（広告・分析・クラッシュ収集も入れない） | §4 のプライバシー方針 |
| minSdk / targetSdk | 26 / 36 | minSdk 26 は将来の Health Connect SDK 要件（API 26+）に合わせた |

## 3. アーキテクチャ

```
tasklock-android/
├── core/   … Android 非依存（純 Kotlin/JVM）。ここがアプリの「ルール」
│   ├── model/     Task, Completion, Verification, LockRule, UnlockGrant, VerificationStatus
│   ├── lock/      LockEvaluator（解除判定）, BlockSnapshot（ブロック判定）
│   ├── verify/    Verifier（検証結果の生成）, UsageTimeCalculator（前面時間の計算）
│   ├── template/  TaskTemplates
│   └── time/      DayBoundary（「1日」の区切り）
└── app/    … Android 依存
    ├── data/      Room エンティティ・DAO、Repository（完了→検証→解除をトランザクションで実行）
    ├── platform/  UsageStatsReader, InstalledApps, AccessibilityStatus
    ├── service/   AppLockAccessibilityService
    └── ui/        MainActivity（ホーム/タスク設定/完了/ロック対象/開示）, BlockActivity
```

判定ロジックを `:core` に置くことで、実機なしでもロック条件・検証レベル・日付境界・利用時間計算をテストできる。

## 4. データモデル（Task → Completion → Verification → Unlock）

```
Task 1 ── * Completion 1 ── * Verification
                │
                └── UnlockGrant（どの Completion で、いつまで解除したか）
LockRule（type + params）── UnlockGrant
LockedApp（ロック対象パッケージ）
```

| テーブル | 主なカラム | ポイント |
|---|---|---|
| `tasks` | category, unit, targetValue, verificationPolicy, **requiredStatus**, targetPackage, active | 解除に必要な最低検証レベルをタスクごとに持つ。削除は論理削除 |
| `completions` | taskId, **day**, reportedValue, startPage, endPage, note, completedAt | 「完了した」という申告のみ。信頼の根拠は持たない |
| `verifications` | completionId, **status**, **method**, **dataJson**, **modelVersion**, **verifiedAt** | 1つの Completion に複数の検証を付けられる。解除判定は最も強い検証で行う |
| `lock_rules` | type, paramsJson, active | MVP は `DAILY_ANY_ONE_TASK` の1件。新ルールは type 追加で拡張 |
| `unlock_grants` | day, ruleId, completionId, grantedAt, expiresAt | ブロック判定は `expiresAt` で行うため日付をまたいでも正しく再ロックされる |
| `locked_apps` | packageName, label | |

### 検証レベル
`UNVERIFIED(0) < SELF_REPORTED(1) < PARTIAL(2) < PHOTO_VERIFIED(3) < VERIFIED(4)`
解除条件は `bestStatus.rank >= task.requiredStatus.rank`。

- 自己申告タスク（学習・読書・運動）: `requiredStatus = SELF_REPORTED`
- 学習アプリ利用時間タスク（資格）: `requiredStatus = VERIFIED`（目標未達は `PARTIAL` で記録され解除されない。再確認すると同じ Completion に新しい Verification が追加される）
- 読書: ページ整合性チェックを通った場合のみ保存（method = `reading_consistency`）。客観データではないため `SELF_REPORTED`

### テンプレートごとの解除条件
「Completion だけでは解除されない」のは内部の話で、自己申告型タスクでは完了時に SELF_REPORTED の Verification が自動で作られる。ユーザーから見れば4テンプレート中3つは「完了」で解除される。

| テンプレート | 自己申告だけで解除 | 必要レベル | 検証内容 | 検証できないとき |
|---|---|---|---|---|
| 問題集を解く（学習） | できる | SELF_REPORTED | 申告値 ≥ 目標 | — |
| 学習アプリで勉強（資格） | **できない** | VERIFIED | 当日開始からの対象アプリ前面時間 ≥ 目標分 | UNVERIFIED/PARTIAL で解除されない。自己申告タスクで解除する（D2 対策により必ず1つ存在） |
| 本を読む（読書） | できる | SELF_REPORTED | ページ範囲とページ数の整合、前回終了+1 より先へ飛んでいないこと | 不整合は完了不可（入力修正で通る） |
| 筋トレ・運動 | できる | SELF_REPORTED | 申告値 ≥ 目標 | — |

仕様との差分（未対応・判断保留）: 学習テンプレートは「問題集の問数」のみ（参考書ページ・学習アプリ記録は未実装）。運動は Health Connect 未連携。PARTIAL は「利用時間が目標未達」の意味で使っており、仕様の「一部条件のみ検証」と厳密には一致しない。読書で章を飛ばした場合の救済はしない（自己申告＋簡易整合性チェックの範囲とする）。

### 変更の不変条件（ChangePolicy、:core で単体テスト済み）
1. ロック中は解除条件に影響するタスクの追加・削除をしない。例外は有効タスク0件のときの追加（初回設定で永久ロックにならないため）
2. 有効タスクが1件以上あるなら、自己申告で解除できるタスクが必ず1件以上ある。VERIFIED 必須タスクだけの構成は、追加時にも削除時にも拒否する
3. 学習アプリ ∩ ロック対象 = ∅。タスク追加時・ロック対象追加時の両方で検査する
4. ロック対象の追加はロック中でも可（制限を強める方向）。外すのは解除中のみ
5. ロック状態はロック対象が1件以上かつ有効な UnlockGrant が無いこと。変更可否の判定は DB を読んで行い、起動直後に空になりうるメモリ上のスナップショットは使わない
6. ホーム・電話・SMS・設定・自アプリはロック対象に登録できず、登録後に既定アプリが変わった場合もブロック判定時に除外する（電話・SMS はそれぞれ既定アプリ1つ。除外は実行時に問い合わせ、DB には保存しない）

### PHOTO_VERIFIED を後から足せるか → **スキーマ変更なしで可能**
- status / method は **文字列で保存**しているため、enum に値を足すだけでよい（既に `PHOTO_VERIFIED` / `camera_ai` を定義済み）
- `ai_result` / `confidence` は `dataJson` に、モデルは `modelVersion` に、時刻は `verifiedAt` に入る
- 画像は保存しない前提なので画像パス用カラムは不要
- 旧バージョンのアプリが未知の status を読んだ場合は `UNVERIFIED` 扱い（安全側）
- UI は「記録済み」「自動で確認済み」の2種類のみ表示（DB は2値に固定しない）

## 5. ブロック設計

### 5.1 AccessibilityService（採用）
1. `typeWindowStateChanged` のみ購読、`canRetrieveWindowContent=false`（画面内容は読まない）
2. イベントのパッケージ名を、メモリ上の `BlockSnapshot`（ロック対象集合 + 最新の UnlockGrant）で判定。イベントごとの DB アクセスはしない
   - **起動直後の未ロード対策（BlockGate）:** スナップショットは未ロードを `null` で表し、「ロック対象なし」と区別する。未ロード中はブロックできないが、直近の前面アプリ（最後に受け取ったウィンドウイベントのパッケージ）を記録し、初回ロード完了時にそれを再判定してブロックする。自アプリ・ホーム等は再判定でもブロックしない
   - **残る限界:** ①未ロード中に開いたアプリは、ロード完了までの間は表示される（この時間は**未計測**）②サービス接続後にイベントが1つも来ないまま対象アプリが前面にある場合は、前面アプリが分からず再判定できない（次のイベントでブロック）③「直近のウィンドウイベント」がキーボードやシステムUIのものだった場合、実際の前面アプリとずれることがある。いずれも実機で確認する（§9.5）
3. ブロック対象なら `BlockActivity` を新しいタスクとして前面に出す。「戻る」はホーム画面へ置き換え
4. 多重起動の間引き（`BlockDebouncer`）: 同じパッケージのイベントが**途切れずに**続く間だけ 700ms 間引く。別パッケージ（ホーム・ブロック画面自身・他アプリ）のイベントを挟めば即リセットするので、「対象アプリ → ブロック → ホーム → すぐ対象アプリ」は時間に関係なく再ブロックされる
5. ロック対象の候補から、自分自身・設定・ホームアプリ・既定の電話アプリ・既定の SMS アプリを除外（緊急連絡・端末操作を妨げない）。ブロック判定時にも同じ除外を実行時に問い合わせる（`InstalledApps.exemptPackages()`。候補一覧・`ChangePolicy.canLockApp`・`BlockGate` で共通）
   - 既定の SMS アプリがすでにロック対象に登録されている場合（除外の導入前に登録した場合や、登録後に既定の SMS アプリを変更した場合）、DB の行は削除せず、ブロックもしない。ロック対象画面では「除外中（既定のSMSアプリ）」と表示する（§9.6-4）

### 5.1.1 ブロック境界（コードで保証できること / OS 仕様上保証できないこと）
| ケース | コードで保証 | 保証できない（OS・端末依存） |
|---|---|---|
| 対象アプリ起動 | ウィンドウ切替イベントを受けたらブロック画面を出す | ブロック画面が出るまでの一瞬の表示 |
| 対象アプリ → ホーム | ホームは対象外（何もしない） | — |
| 最近使ったアプリから復帰 | イベントを受けたら再ブロック（間引きは別パッケージを挟むとリセット） | — |
| Activity遷移・アプリ内の別Activity | 遷移ごとのイベントで再ブロック | PiP・フローティング・分割画面ではイベントが来ないことがある |
| ブロック画面で BACK | ホームへ移動してから閉じる（対象アプリに戻らない） | — |
| サービス停止後 | ブロックしない。アプリを開いたときに警告表示 | 停止の防止・通知。クラッシュが続くと OS がサービスを無効化 |
| 端末再起動後 | 有効設定は保持され、ロック解除後に OS が再接続 | 省電力機能等による停止（**要実機確認**） |
| 自アプリが前面 | ブロックしない | — |
| ロック後に既定のホーム/電話/SMS アプリが変わる | 判定時に除外 | — |
| バックグラウンドからの Activity 起動 | ユーザー補助サービスは例外扱いの想定 | Android 15 以降の制限強化の影響（**要実機確認**） |

### 5.2 回避経路（Android の仕様上防げないもの）
| 経路 | 対策 |
|---|---|
| 設定でユーザー補助をオフ／アプリの強制停止 | 防げない。ホームに「ブロック機能がオフです」を表示 |
| アプリのアンインストール・データ消去 | 防げない（デバイス管理者権限は使わない方針） |
| 端末の日時を変更 | 未対策。Phase 2 で `elapsedRealtime` との突き合わせを検討 |
| ブラウザ版 SNS・通知からの返信・ウィジェット | 未対策（ブラウザごとブロックすると学習にも支障が出るため） |
| セーフモード起動 | 防げない |
| Advanced Protection Mode（Android 16+/17） | `isAccessibilityTool=false` のサービスは権限付与が拒否・取り消しされる。**このモードの利用者には提供不可** |
| ロック中にロック対象を外す／タスク削除 | **対策済み**（ChangePolicy + Repository で拒否） |
| ロック中に簡単なタスクを追加 | **対策済み**（方式B。有効タスク0件のときの追加のみ可） |
| 解除中に翌日以降のタスクを簡単なものへ差し替える | 許容（解除中に決めたことが翌日の条件になる、というコミットメントの設計） |
| 既定の SMS アプリを、ロック対象の SMS 対応アプリに変更する | **許容**（§9.6-4）。緊急時の通信手段を確実に使えることを優先した設計判断。既定の SMS アプリになれるのは SMS 機能を持つアプリに限られる |

マーケティングでは「絶対に解除できない」とは言わず「意志力に頼らない仕組み」と表現する。

### 5.3 UsageStatsManager によるブロック（Phase 1 では不採用）
UsageStats でブロックする場合は、常駐フォアグラウンドサービスで `queryEvents` を1〜2秒間隔でポーリングし、前面アプリを推定する方式になる。
- 検知まで数秒の遅れがあり、SNS を一瞬開けてしまう
- Android 14+ はフォアグラウンドサービスの type 宣言が必要で、該当 type が無く `specialUse` となり Play での説明が必要
- 常時ポーリングによる電池消費
よって「AccessibilityService が使えない端末向けの代替手段」として Phase 2 以降で検討する。

### 5.4 UsageStatsManager（検証用途）の注意点
- 権限は `PACKAGE_USAGE_STATS`（ユーザーが「使用状況へのアクセス」で許可）。付与判定は AppOps で行う
- `queryUsageStats` の日次集計はバケット境界の都合で「今日0時から」を正確に切り出せないため、`queryEvents` の生イベントから計算
- イベント種別: API 29 で `MOVE_TO_FOREGROUND/BACKGROUND` → `ACTIVITY_RESUMED/PAUSED` に改名（値は同じ 1/2）。画面OFF(16)・シャットダウン(26)で区間を打ち切る
- 同一アプリ内の画面遷移で RESUMED/PAUSED の順序が前後するため、前面 Activity 数を数えて 0↔1 の遷移だけを区間とする
- イベント保持期間は OS 依存で数日。当日分の検証にだけ使う
- **「前面に表示していた時間」であって「勉強していた時間」ではない**ことを UI に明記済み

## 6. 永続化・バックアップ

- Room DB `tasklock.db` のみ。サーバー送信なし、アカウントなし、ユーザーIDの発行なし
- `allowBackup=false` + `dataExtractionRules`（Android 12+ のクラウド・端末間転送の両方）+ `fullBackupContent`（11以下）で全ドメインを除外
  - 理由: 一部メーカー端末では `allowBackup=false` だけでは端末間転送が止まらないため、ルールでも明示的に除外
- **帰結**: アンインストール・再インストール・機種変更でタスク履歴とロック設定は消える。ユーザー向けにストア説明・ヘルプで明記すること
- 課金状態は DB に依存させず、起動時に Google Play から毎回取得する（§8）ため、再インストールしても有料機能は復元される

| Health Connect（Phase 2） | 歩数検証 | `READ_STEPS` 宣言、権限説明 Activity（Android 13以下: `ACTION_SHOW_PERMISSIONS_RATIONALE`、14+: `VIEW_PERMISSION_USAGE` の activity-alias）、Play Console での健康データ申告 |

データ安全性セクション: 端末内でのみ処理しサーバー送信しないため「収集なし・共有なし」で申告できる見込み。ただし公開前に、実装に基づき Play の定義で再確認すること。プライバシーポリシー URL は Accessibility 利用アプリとして必須。

Android 13+ の「制限付き設定」: ストア以外から導入した APK ではユーザー補助の許可が灰色になることがある。その場合はアプリ情報の右上メニューから「制限付き設定を許可」。

### 1. 現在利用可能な回避経路（確定: 追加実装なし）
現在の設計では、次を意図的にブロック対象外としている。

- 電話（既定の電話アプリ）
- 設定
- ホーム画面
- TaskLock 自身

これらはロック対象アプリの選択肢から除外されており、ブロック判定時にも実行時に除外される（`InstalledApps.exemptPackages()`、§5.1-5）。
特に電話は緊急時の連絡手段として常に使え、110番・119番を含む緊急通報を妨げない。

また、設定から「ユーザー補助」→「タスクロック」をオフにすれば、ロック機能自体を止められる。この経路は緊急時の最終的な解除手段として残す。
これらは「防げない回避経路」（§5.2）として扱い、完全な強制ロックを目的としない現在の設計方針と整合する。

- この項目に対する追加の実装は行わない
- ユーザー補助がオフにされた事実・理由の記録は、OS の仕様上確実に取得できないため**保留**とする（現行どおり、アプリを開いたときに「ブロック機能がオフです」を表示するのみ）

### 2. 緊急解除機能（原則のみ確定・数値は保留）
現在、アプリ内に専用の「緊急解除」機能はない。
そのため、緊急時にはユーザー補助の設定まで移動して TaskLock を無効化する必要がある。また、この操作はタスク達成による通常の解除と異なり、現在はアプリ内で解除理由として記録されない。

位置づけ: 生命に関わる緊急時は、常にロック対象外の電話アプリ（項目1）で対応できる。アプリ内の緊急解除が主に担うのは「急ぎでロック対象アプリ（例: LINE）を使う必要がある」場面であり、制限が弱すぎると新たな回避経路になる。

**確定する原則**
- 解除理由を「タスク達成」と「緊急解除」に分けて記録する
- 緊急解除はタスクの「達成」として扱わない（ホームの「✅ 達成」表示や、今後の統計に含めない）
- 緊急解除は「Task → Completion → Verification → Unlock」のフローを通らない別経路とし、`LockEvaluator` の判定には手を加えない
- **緊急解除中も `ChangePolicy` の判定は「ロック中」として扱う**（タスクの追加・削除、ロック対象からの除外は不可のまま）
  - 理由: 現行の `isLockedNow()` は最新の `UnlockGrant` が有効かどうかだけで判定しているため、緊急解除を通常の解除記録と同じ扱いで保存すると、緊急解除の直後に §4「変更の不変条件」が外れ、新たな回避経路になる

**保留する事項**（実際の利用状況を踏まえて、別途要件を確定してから着手する）
- 解除の有効期限（当日の終わりまで／N 分間）
- 意図的な手間の方法と強さ（待機時間、確認用の文字列入力など）
- 使用回数の上限と、リセットの単位（1日／週／月）
- 緊急解除の入口（ブロック画面／ホーム）
- 記録先（`UnlockGrant` に解除理由を追加して `completionId` を任意にする／別テーブル）。いずれの場合も Room のマイグレーション（v1→v2）が必要で、既存の履歴を破棄するマイグレーションは使わない

### 3. 連絡・移動等の重要アプリに対する警告（確定）
現在、電話アプリは除外されているが、SMS・LINE・地図・乗換案内など、緊急時や日常の連絡・移動に使うアプリはロック対象として選択できる。
また、ロック中はロック対象から外せない（方式B）ため、ロック中に誤って登録すると、その日のタスクを達成するまで戻せない。

この機能は「連絡用アプリを正確に分類する」ものではなく、**重要な通信・移動手段を誤ってロック対象に入れる前に、ユーザーに気づかせる**ためのものである。

**判定方法**（次のいずれかに該当すれば「連絡・移動等の重要アプリ」として警告する）
- `smsto:` のインテント（`ACTION_SENDTO`）を受け取れるアプリ → SMS 系
- `geo:` のインテント（`ACTION_VIEW`）を受け取れるアプリ → 地図・位置情報系
- インテントでは検出できない主要アプリの**固定リスト**
  - `jp.naver.line.android`（LINE）
  - `jp.co.yahoo.android.apps.transit`（Y!乗換案内）

**判定の方針**（2026-09-27 確定）
- **実行時に判定する。** 確認画面を表示するたびに、追加するアプリだけを対象に判定する。判定結果は DB に保存しない（項目4の既定の SMS アプリの除外と同じ考え方）
- **固定リストは最小限とする。** 入れる基準は「多くの人が使っていて、止めると連絡や移動が難しくなるのに、インテントでは検出できない、よく知られたアプリ」。**パッケージ名は実際に確かめたものだけを登録する**（推測で書かない）
  - 2026-09-27 に Pixel 9a（`pm list packages`）で確かめたのは上の2つ。Y!乗換案内は `geo:` では検出されなかった（`pm query-activities` で確認）
  - ジョルダン乗換案内・NAVITIME の乗換アプリは、パッケージ名を確かめられていないため入れない。確かめられた時点で必要性を再検討する
  - 学校の連絡や見守りのアプリ（すぐーる、みてねGPS、ファミリー リンクなど）は、家庭によって重要性が大きく異なるため入れない
- **想定していないアプリが検出されても、警告の対象として扱う。** 例: 船の航法アプリ（ActiveCaptain、`com.garmin.android.marine`）は `geo:` で検出される。警告は登録を禁止しないため、判定が多少広くても動作上の制約は増えない
- `ApplicationInfo.category`（SOCIAL など）による判定は採用しない。連絡用に限らず Instagram・X なども一律に警告対象となり、警告の意味が薄れるため
- 既定の SMS アプリ・電話アプリなど、項目4などで除外しているアプリは候補に出ないため、警告の対象にならない。そのため `smsto:` の判定は、2026-09-27 時点の Pixel 9a では既定の SMS アプリ（メッセージ）しか該当せず、項目3の警告として実機では確認できない（判定ロジックは単体テストで確認する）。SMS 対応アプリが複数ある端末や、既定の SMS アプリを切り替えた場合に意味を持つ

**実装上の構成**
- **Android への問い合わせは `InstalledApps` で行う。** `smsto:`・`geo:` を受け取れるアプリのパッケージ名を、呼ばれるたびに問い合わせる
- **判定の中心は `:core` の純粋関数とする。** 追加するアプリ・`smsto:` の受け手・`geo:` の受け手・固定リストを受け取り、警告の対象となるアプリを返す。単体テストで結果を固定する
- **マニフェストの `<queries>` に次の2つを追加する**（Android 11 以降でアプリからこの2種類の受け手を調べられるようにするため）
  - `ACTION_SENDTO` ＋ `scheme="smsto"`
  - `ACTION_VIEW` ＋ `scheme="geo"`
  - 固定リストは、既に見えているランチャーのアプリのパッケージ名と照合するだけなので、`<package>` の追加は不要。`QUERY_ALL_PACKAGES` は使わない
- `ChangePolicy`・`LockEvaluator`・`BlockSnapshot` の判定の意味と、DB スキーマは変えない

**警告の仕方**（項目6の決定事項1により改訂）
- 警告は、項目6の確認画面（ロック対象の追加を反映する直前の画面）の「重要なアプリに関する警告」の欄に表示する。チェックしたとき（下書きの段階）には出さない。個別の確認ダイアログは設けない
- ロック対象への登録は拒否しない。確認画面の「確定」を押した場合のみ登録する（`ChangePolicy` の判定は変更しない）
- 文言は、登録すると何が起きるかを具体的に伝えるものとする
  - 該当するアプリごとに: 「このアプリは連絡・移動に使用される可能性があります」
  - ロック中に追加する場合の「今日のタスクを達成するまでロック対象から外せません」は、項目6の確認画面の「ロックに関する注意」の欄で、追加するアプリ全体に対して表示する（警告の欄では繰り返さない）

### 4. SMS アプリの既定除外（確定）
既定の SMS アプリを、電話アプリと同様にロック対象から除外する。目的は電話と同じく、緊急時の通信手段を確保することである。

- **除外対象は既定の SMS アプリ1つだけ**とする（`Telephony.Sms.getDefaultSmsPackage()`。取得できない場合は何も追加しない）。+メッセージや LINE などを一律に除外することはしない（それらは項目3の警告で扱う）
- **除外は実行時に評価する。** `InstalledApps.exemptPackages()` が呼ばれるたびに既定の SMS アプリを問い合わせ、`BlockGate` のブロック判定・ロック対象候補の一覧・`ChangePolicy.canLockApp` のすべてでその結果を使う。DB に除外パッケージを保存するような固定的な除外にはしない。既定の SMS アプリが変わった場合は、次の判定から除外対象も変わる（既定のホーム/電話アプリと同じ扱い。§5.1-5、§5.1.1）
- **登録済みの行は DB から削除しない。** 既定の SMS アプリがすでにロック対象として登録されている場合、DB 上の登録状態は保持したまま、実行時の除外によってブロックしない。ロック対象の画面では、その行に「除外中（既定のSMSアプリ）」と表示する
- **既定の SMS アプリを変更することで除外対象が変わることは、仕様上許容する回避経路とする。** ユーザーが別の SMS アプリ（ロック対象に登録済みのものを含む）を既定に変更すれば、そのアプリはブロックされなくなる。既定の SMS アプリになれるのは SMS 機能を持つアプリに限られるが、これは「安全だから問題ない」という判断ではなく、**緊急時の通信手段を確実に使えることを優先して、この経路を意図的に許容する**という設計判断である。実装時に §5.2 の回避経路の表へ追記する
- 実装時には §4 の不変条件6、§5.1-5、§5.1.1 の表を更新し、§10 に実機テスト（既定の SMS アプリがロック対象の候補に出ない／登録済みでもブロックされず「除外中」と表示される／既定の SMS アプリを変更すると除外対象が切り替わる）を追加する

### 6. ロック対象の選択を「確定」で反映する（確定）
**背景（2026-09-27 の実機確認で判明）**
- ロック対象の画面では、チェックを押した時点で DB に保存される（`LockedAppsScreen` → `MainViewModel.setLocked` → `addLockedApp` / `removeLockedApp`）。右上の「完了」は画面を閉じるだけ
- ロック中は対象から外せない（方式B、`ChangePolicy.canUnlockApp`）。そのため、ロック中に押し間違えると、その日のタスクを達成するまで戻せない
- ロックの成立条件は「ロック対象が1つ以上、かつ今日まだ解除されていない」（`LockEvaluator.isLockedAt`）で、タスクの有無によらない。初回利用時は、1個目にチェックを入れた時点でロックが始まり、2個目以降の押し間違えはその日は外せない（実機で確認：タスク0件でも対象を選んだ直後に「🔒 ロック中」）

**方針（案）**
- **チェック操作は下書きとする。** 画面内で自由に入れ外しでき、DB と実際のロック状態には影響しない
- **「確定」が保存・状態反映の境界となる。** 確定を押した時点で、下書きと保存済みの差分（追加・削除）を反映する
  - 可否の判定は、確定を押した時点のロック状態で `ChangePolicy` を使って行う（判定の意味は変えない）。画面を開いている間に日付が変わって再びロックされた場合も、確定時点の状態で判定する
  - 差分の反映は、すべて成功するか、何も反映しないかのどちらかとする（一部だけ反映しない）。拒否された場合は理由を表示し、下書きを残す
- **確定前に確認画面を表示する。** 次の3つを、見出しを分けて表示する（該当するものだけ）
  1. **追加・変更されるロック対象:** 追加するアプリと外すアプリの一覧
  2. **重要なアプリに関する警告:** 追加するアプリのうち、項目3の判定（`smsto:`・`geo:`・固定リスト）に該当するもの。項目3の警告はこの確認画面で表示し、チェック時（下書きの段階）には出さない
  3. **ロックに関する注意:** ロック中に追加する場合は「追加したアプリは、今日のタスクを達成するまで外せません」。ロックしていないときに確定して、それによってロックが始まる場合は、その旨
  - 追加がなく、外すだけの場合（ロックしていないときに限られる）は、確認画面を省略する（決定事項3）
- **確定せずに戻る／閉じる場合は、変更の破棄を確認する。** 下書きに変更がない場合は確認しない
- **登録済みのアプリをロック中に外せない制約は維持する。** 下書きでも、ロック中は保存済みの対象のチェックを外せない（外せるように見せない）
- 既定の SMS アプリの扱い（項目4）は変えない
- DB スキーマは変更しない。`:core` の判定（`LockEvaluator`・`ChangePolicy`・`BlockGate`）の意味は変えない。変更は画面と、差分をまとめて反映する処理に限る

**決定事項（2026-09-27）**
1. **項目3（重要アプリへの警告）との関係 → 確定時の確認画面にまとめる**
   - 理由: 重要アプリの警告も、ロック中に追加するアプリの確認も、「選んだ内容を確定する直前に最終確認させる」という同じ境界にある。別々の画面にすると確認が分散する
   - 帰結: 項目3の「警告の仕方」（登録時の確認ダイアログ）は、この確認画面の中の表示に置き換わる。項目6を確定するときに項目3の記述を改める。実装は項目6を項目3より先に行う
2. **初回利用時の流れ → タスクを先に設定する**
   - 流れ: タスクを決める → ロックするアプリを選ぶ（下書き） → 確認画面 → 確定
   - 理由: 実機テストで確認した問題は、ロック対象を選んだ瞬間にロックが始まり、タスクがない状態でもユーザーを拘束することだった。タスクを先に決めれば、アプリの目的と状態の移り変わりが一致する
   - **タスクの設定はロック開始の条件にしない。** ロックが始まるのは、これまでどおり「ロック対象を確定した時点」（ロック対象が1つ以上、かつ今日まだ解除されていない。`LockEvaluator` の意味は変えない）
   - 有効なタスクが0件のときにロック対象の画面を開こうとした場合は、先にタスクの設定へ案内する（ホームの「アプリを選ぶ」、ブロック機能の案内からの導線を含む）。これは画面の流れの変更で、`ChangePolicy` の判定（有効タスク0件のときはロック中でもタスクを追加できる、など）は変えない
3. **確定ボタンの名前と位置、確認画面を出す条件**
   - 名前は「確定」とする（今の「完了」を置き換える）。「完了」は画面を閉じるだけにも読めるが、「確定」は下書きから DB へ反映する境界であることを示せる
   - 確認画面では、画面の最下部に主要な操作として「確定」を置く
   - ロック対象の画面の下部のボタンを「確定」とする。押した時点で、まず下書きと保存済みの差分を判定する
     - 外すだけの場合: その場で反映して画面を閉じる（確認画面は出さない）
     - 追加を含む場合（追加と外すの両方を含む場合も含む）: 確認画面へ進む。この時点では DB にもロック状態にも反映しない
   - 確認画面の最下部にも「確定」を置く。追加を含む場合は、確認画面の「確定」を押した時点で初めて DB とロック状態に反映する
   - 2つの「確定」の役割: ロック対象の画面の「確定」は「選択内容を確定して次へ進む」、確認画面の「確定」は「最終的に変更を確定する」。同じ名前が2段階になるため、確認画面側を「この内容で確定」などにするかは、実装時の UI の詳細として扱う
   - 流れ
     - 外すだけ: アプリ選択（下書き） → 「確定」 → 反映
     - 追加あり: タスク設定（初回のみ） → アプリ選択（下書き） → 「確定」 → 確認画面 → 「確定」 → 反映
   - ロック中は保存済みの対象を外せないため、外すだけの確定はロックしていないときにだけ起こる（制約は変えない）

**未決定事項**
- なし（2026-09-27 確定。あわせて項目3の「警告の仕方」、§9.6 の表、§5 の実装順を改めた）

**実機テスト（実装時に §10 へ追加する）**
- 下書きで入れ外ししても、確定するまでブロックされない
- 確定せずに戻ると破棄を確認し、破棄すれば保存済みの状態に戻る
- ロックしていないときに外すだけの変更を「確定」すると、確認画面を出さずに反映される
- ロック中に追加を確定すると確認が表示され、確定後は外せない
- ロック中は、保存済みの対象のチェックを外せない
- 初回利用時（タスク0件・ロック対象0件）: ロック対象の画面より先にタスクの設定へ案内され、タスクを設定してもロックは始まらない。ロック対象を確定した時点でロックが始まる
- 確認画面: 重要なアプリ（項目3の判定に該当）を追加するとき、警告が確認画面の中に表示され、チェック時には出ない

### CI のデバッグ APK の署名（2026-09-27 固定）
- **背景:** 以前の CI は、実行ごとに作られる使い捨てのデバッグ鍵で署名していた。そのため別の実行の APK へは上書き更新できない（CI run #5 の APK を `adb install -r` → `INSTALL_FAILED_UPDATE_INCOMPATIBLE`）
- **方式:** 固定のデバッグ鍵（PKCS12、エイリアス `androiddebugkey`、パスワードは Android 標準のデバッグ用の値）を GitHub Secret `TASKLOCK_DEBUG_KEYSTORE_B64`（Base64）に保管する。app-build ジョブはビルド前に、この鍵を `~/.android/debug.keystore` に置き、AGP が参照する場所を環境変数 `ANDROID_USER_HOME` で同じ場所に明示する。`build.gradle.kts` は変更しない（CI run #7 では場所を明示しなかったため、AGP が別の場所に作った鍵（証明書 SHA-256 `8746057a…6b8081`）で署名し、検証の手順で失敗した）
- **検証:** ビルド前に鍵の証明書を、ビルド後に APK の証明書を、それぞれ期待値の SHA-256 と照合する。一致しなければジョブを失敗させる。Secret が未登録の場合も失敗させる（使い捨ての鍵で署名した APK を作らない）。ログに出すのは証明書の SHA-256 だけで、Secret と鍵の中身は出さない
- **期待値（固定鍵の証明書 SHA-256）:** `1e6152d6125d65401b2e65d47eda4c11e7af93708c2bfc0e58ab55d3dde9e090`（`CN=Android Debug, O=Android, C=US`、有効期限 2054-02-12）
- **適用範囲:** app-build ジョブのみ（core-test は対象外）
- **鍵の保管:** 原本は開発用 PC の `~/.android/debug.keystore`。デバッグ鍵のため、別のバックアップは作らない。失った場合は新しい鍵に切り替え、Secret と期待値を更新して、端末のアプリを再インストールする。Play 公開用の鍵は別に作り、この鍵を流用しない
- **手元でのビルド:** 同じ鍵を `~/.android/debug.keystore` に置けば、手元でビルドした APK と CI の APK は相互に上書き更新できる
- **移行前の端末の状態（Pixel 9a、2026-09-27 確認）:**
  - インストール済み APK の証明書 SHA-256: `b87d73954741b8ee0bb1c80a24d275d479c82fb83c2c454f2c8c57257d546a09`（`CN=Android Debug`。CI の使い捨て鍵）
  - CI run #2 の APK との照合: **未実施**

- **内部の各段階（サービス接続 → ロード開始 → ロード完了 → 再判定）:** 現在のコードにはログが無いため**測れない**。測る場合はデバッグビルド限定のログ追加が必要（未実装・要承認）
